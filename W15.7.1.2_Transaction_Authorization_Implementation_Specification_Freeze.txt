APPROVED ARCHITECTURAL PRINCIPLES
----------------------------------

1. Transaction Authorization is distinct from Authentication.

2. Transaction Authorization is distinct from Authentication Assurance.

3. Transaction Authorization is distinct from Business Authorization.

4. W15.7 consumes W15.6 AuthenticationAssuranceContext.

5. W15.7 MUST NOT implement MFA.

6. W15.7 MUST NOT implement WebAuthn.

7. W15.7 MUST NOT manufacture A2/A3 assurance.

8. A3 Authentication Assurance does NOT automatically authorize a
   transaction.

9. W15.7 MUST bind authorization to the exact transaction.

10. Principal binding is mandatory.

11. transaction_id binding is mandatory.

12. operation binding is mandatory.

13. amount binding is mandatory where applicable.

14. currency binding is mandatory where applicable.

15. merchant/service/recipient binding is mandatory where applicable.

16. Relevant risk context MUST remain bound according to central policy.

17. Transaction representation MUST be deterministic and canonical.

18. Binary floating-point equality MUST NOT be used for monetary
    authorization.

19. Nonce uniqueness MUST be enforced at the trusted application boundary.

20. authorization_id MUST distinguish authorization instances from
    business transaction IDs where appropriate.

21. Authorization MUST be single-use.

22. Consumption MUST be atomic.

23. Concurrent consumers MUST NOT both succeed.

24. Replay MUST fail closed.

25. Expired authorization MUST fail closed.

26. Revoked authorization MUST fail closed.

27. Illegal lifecycle transitions MUST fail closed.

28. Caller-controlled approval assertions MUST NOT create trusted
    transaction authorization.

29. User approval MUST be bound to the exact canonical transaction.

30. Trusted server/application time determines validity and expiry.

31. Caller-controlled time MUST NOT determine validity.

32. Material risk changes MUST invalidate or require fresh authorization
    according to centrally supplied policy.

33. W15.7 MUST NOT bypass AuthorizationService.

34. Business services MUST NOT implement transaction authorization policy.

35. Business services MUST NOT implement MFA policy.

36. Policy MUST be centrally supplied.

37. Monetary thresholds MUST be centrally governed.

38. Audit evidence MUST correlate authorization and transaction.

39. Raw credentials and security secrets MUST NOT enter audit evidence.

40. No cryptographic transaction-signing guarantee may be claimed unless
    actual cryptography is implemented and tested.

41. ZITADEL is outside the current W15.7 implementation boundary.

42. Keycloak is outside the current W15.7 implementation boundary.

43. WebAuthn/passkeys are outside the current W15.7 implementation boundary.

44. AuthenticationService remains unchanged.

45. Principal remains unchanged.

46. IdentityProvider remains unchanged.

47. SessionIdentityProvider remains unchanged.

48. AuthorizationService remains unchanged unless a separately reviewed
    architectural necessity is established.


PROVIDER-NEUTRALITY FREEZE
--------------------------

W15.7 MUST consume provider-neutral internal authentication assurance.

The W15.7 domain/application layer MUST NOT import or depend upon:

    ZITADEL
    Keycloak
    WebAuthn
    passkey SDKs
    OIDC SDKs
    SAML SDKs
    provider-specific user objects
    provider-specific session objects
    provider-specific token objects

Future identity-provider integration MUST occur through the Identity
Adapter and W15.6 Authentication Assurance boundary.


FUTURE ZITADEL / KEYCLOAK BOUNDARY
-----------------------------------

Future architecture:

    ZITADEL / Keycloak
        ->
    Identity Adapter
        ->
    Validated Authentication Evidence
        ->
    W15.6 Authentication Assurance
        ->
    AuthenticationAssuranceContext
        ->
    Authorization Policy
        ->
    W15.7 Transaction Authorization

The fundamental W15.7 transaction-authorization model SHOULD remain
unchanged when an external IAM provider is introduced.

Any future change to W15.7 security semantics requires a new architecture
and security review.


FUTURE WEBAuthn / PASSKEY BOUNDARY
-----------------------------------

Future architecture MAY provide:

    WebAuthn/passkey
        ->
    Identity Adapter
        ->
    validated authentication evidence
        ->
    W15.6 A3 Authentication Assurance
        ->
    W15.7 Transaction Authorization

WebAuthn authentication MUST NOT itself constitute transaction approval.
