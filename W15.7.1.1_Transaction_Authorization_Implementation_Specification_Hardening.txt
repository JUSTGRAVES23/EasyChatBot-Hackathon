W15.7.1.1 — TRANSACTION AUTHORIZATION IMPLEMENTATION SPECIFICATION HARDENING
==========================================================================

STATUS
------
W15.7.0.4 Contract Freeze: COMPLETE
W15.7.1 Implementation Specification: COMPLETE
W15.7.1.1 Compatibility Hardening: COMPLETE
Production implementation: NOT STARTED

PURPOSE
-------
Harden W15.7.1 so the implementation remains provider-neutral and
compatible with the future introduction of:

    - ZITADEL
    - Keycloak
    - WebAuthn / passkeys

The W15.7.0.4 Transaction Authorization Contract remains FROZEN.


1. PROVIDER-NEUTRALITY REQUIREMENT
----------------------------------

W15.7 Transaction Authorization MUST consume provider-neutral
authentication assurance.

W15.7 MUST NOT directly depend on:

    ZITADEL
    Keycloak
    WebAuthn
    passkey SDKs
    OIDC SDKs
    SAML SDKs
    provider-specific token objects
    provider-specific session objects


2. FUTURE IAM COMPATIBILITY
---------------------------

The W15.7 domain/application contract MUST remain compatible with:

    ZITADEL-backed identity
    Keycloak-backed identity
    future alternative identity providers

without requiring a redesign of the transaction-authorization domain
model.

Future provider integration belongs behind the Identity Adapter boundary.


3. WEBAuthn / PASSKEY COMPATIBILITY
-----------------------------------

WebAuthn/passkeys are authentication mechanisms.

They MAY provide evidence supporting stronger authentication assurance,
including A3 phishing-resistant authentication.

However:

    WebAuthn authentication
        !=
    transaction authorization

A successful WebAuthn/passkey authentication MUST NOT by itself authorize
a transaction.

W15.6 consumes and evaluates the resulting authentication evidence.

W15.7 consumes the resulting AuthenticationAssuranceContext.


4. W15.6 / W15.7 BOUNDARY
--------------------------

The boundary MUST remain:

    Identity Provider
        ->
    Identity Adapter
        ->
    Validated Authentication Evidence
        ->
    W15.6 Authentication Assurance
        ->
    AuthenticationAssuranceContext
        ->
    Authorization Policy
        ->
    W15.7 Transaction Authorization


W15.7 MUST NOT:

    - validate external IAM tokens
    - validate OIDC claims
    - validate SAML assertions
    - validate WebAuthn credentials
    - implement MFA
    - calculate authentication assurance independently
    - manufacture A2/A3
    - replace W15.6 freshness logic


5. STABLE W15.7 INPUT
---------------------

W15.7 MUST consume stable internal concepts rather than external
identity-provider types.

Expected stable inputs include:

    principal_id
    AuthenticationAssuranceContext
    required_assurance_level
    transaction_id
    authorization_id
    canonical transaction representation
    approval evidence
    nonce
    trusted clock
    authorization policy


6. ASSURANCE SEMANTICS
----------------------

The implementation MUST preserve:

    A0 < A1 < A2 < A3

Higher authentication assurance does NOT automatically imply:

    - business authorization
    - transaction authorization
    - permission for every operation

The implementation MUST preserve the distinction:

    Authentication
        !=
    Authentication Assurance
        !=
    Business Authorization
        !=
    Transaction Authorization


7. NO PROVIDER LEAKAGE
----------------------

Provider-specific concepts MUST NOT leak into the W15.7 domain model.

Examples of prohibited domain dependencies:

    ZitadelUser
    ZitadelSession
    KeycloakToken
    KeycloakUser
    WebAuthnCredential
    PasskeyCredential

Provider-specific data MUST be adapted before entering W15.6/W15.7.


8. FUTURE MIGRATION EXPECTATION
------------------------------

When ZITADEL or Keycloak is introduced later, expected changes are
primarily at:

    Identity Provider integration
    Identity Adapter
    Authentication Assurance evidence mapping
    configuration
    integration tests

The W15.7 transaction authorization domain contract SHOULD remain stable.

If future IAM integration requires changing W15.7 security semantics,
that change requires a new architecture/security review.


9. FUTURE WEBAuthn EXPECTATION
------------------------------

When WebAuthn/passkeys are introduced later:

    WebAuthn/passkey
        ->
    Identity Adapter
        ->
    validated authentication evidence
        ->
    W15.6 A3 assurance
        ->
    W15.7 transaction authorization

W15.7 MUST continue to independently bind:

    principal
    transaction
    operation
    amount
    currency
    merchant/service
    recipient where applicable
    risk context where applicable
    nonce
    authorization instance
    approval evidence
    validity period


10. TRANSACTION APPROVAL REMAINS INDEPENDENT
--------------------------------------------

Even when authentication is phishing-resistant, W15.7 MUST still require
transaction authorization according to policy.

Example:

    User authenticates with WebAuthn
        ->
    A3 Authentication Assurance
        ->
    Authorization Policy permits operation
        ->
    Exact transaction presented
        ->
    User approves exact transaction
        ->
    W15.7 authorization created
        ->
    Single-use atomic consumption
        ->
    Business operation


11. NO ARTIFICIAL A3
--------------------

W15.7 MUST NEVER convert:

    successful password login
    successful generic MFA
    valid session
    valid ZITADEL token
    valid Keycloak token

directly into A3.

Authentication assurance is determined by W15.6 according to validated
evidence and centrally supplied policy.


12. IMPLEMENTATION FILE BOUNDARY
--------------------------------

The approved initial W15.7 implementation remains:

    backend/app/domain/identity/transaction_authorization.py

    backend/app/application/identity/transaction_authorization.py

    backend/tests/security/test_transaction_authorization.py

No ZITADEL, Keycloak, or WebAuthn implementation is authorized in these
files.


13. FORBIDDEN IMPLEMENTATION EXPANSION
--------------------------------------

W15.7 implementation MUST NOT expand into:

    external IAM integration
    MFA implementation
    WebAuthn implementation
    passkey registration
    OIDC token validation
    SAML validation
    payment provider integration
    money movement
    production financial execution
    cryptographic transaction signing


14. FUTURE ARCHITECTURE EXTENSION
---------------------------------

Future architecture MAY add:

    ZITADEL Identity Adapter
    Keycloak Identity Adapter
    WebAuthn/passkey authentication support
    authentication evidence validation
    stronger assurance policies

without changing the fundamental W15.7 transaction authorization model.


15. REQUIRED COMPATIBILITY TEST
-------------------------------

W15.7 security tests MUST establish that transaction authorization
depends on the internal authentication assurance contract and NOT on a
specific external identity provider.

The tests MUST NOT import:

    ZITADEL
    Keycloak
    WebAuthn

as part of the W15.7 domain/application implementation.


16. 4-EYES REVIEW REQUIREMENT
-----------------------------

The independent review MUST explicitly verify:

    - provider-neutral W15.7 domain
    - no ZITADEL coupling
    - no Keycloak coupling
    - no WebAuthn coupling
    - W15.6/W15.7 separation
    - A3 does not imply transaction approval
    - transaction binding remains independent
    - AuthorizationService remains independent
    - future IAM integration can occur through the Identity Adapter


17. FREEZE CONDITION
-------------------

W15.7.1 implementation specification may be frozen only after the
compatibility requirements in this artifact are reviewed and accepted.

Until then:

    Production implementation = NOT AUTHORIZED
