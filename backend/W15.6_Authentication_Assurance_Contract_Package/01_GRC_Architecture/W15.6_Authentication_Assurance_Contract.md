# W15.6 — Authentication Assurance Contract

## 1. Objective

Authentication Assurance answers:

> How strongly and how recently was this principal authenticated?

It is distinct from:
- Authentication: who are you?
- Authorization: may you perform this action?
- Transaction Authorization: did you approve this exact high-risk transaction?

## 2. Assurance Levels

### A0 — Authenticated Session
Suitable for normal low-risk operations.

Minimum:
- authenticated principal
- active account
- valid session/token
- no assurance requirement beyond normal authentication

### A1 — Sensitive Account Operation
Examples:
- password change
- email/phone change
- security-profile inspection
- MFA/security-factor administration

Minimum:
- authenticated principal
- recent reauthentication
- MFA where policy requires it
- assurance freshness enforced centrally

### A2 — High-Risk Operation
Examples:
- purchase
- subscription modification
- payment-method change
- refund
- other high-impact account operation

Minimum:
- recent step-up authentication
- MFA
- assurance evidence sufficient for policy
- operation-specific authorization gate

### A3 — Critical / High-Value Operation
Examples:
- high-value financial operation
- especially sensitive security or financial action

Minimum:
- phishing-resistant authentication (WebAuthn/passkey preferred)
- user verification
- recent step-up
- transaction-bound approval
- audit evidence
- replay protection

## 3. Contract Principles

1. Business services MUST NOT implement their own MFA orchestration.
2. Business services request an assurance requirement.
3. The central assurance component evaluates evidence and policy.
4. Assurance MUST NOT be silently downgraded.
5. Freshness is policy-controlled, not hard-coded independently by each service.
6. A successful authentication event does not automatically authorize a transaction.
7. Transaction authorization remains an EasyChatBot application responsibility.
8. External IAM claims are untrusted input until validated by the Identity Adapter.
9. Authorization and assurance are separate decisions.
10. High-risk operations require explicit, auditable policy gates.

## 4. Proposed Request Context

Conceptual contract:

AuthenticationAssuranceContext
- principal_id
- assurance_level
- authentication_time
- assurance_time
- authentication_method
- authentication_strength
- user_verified
- phishing_resistant
- issuer
- subject
- session_id / token reference
- evidence identifiers
- policy_version

Sensitive raw credentials, access tokens, refresh tokens, OTP secrets, and WebAuthn private material MUST NOT be placed in application logs or ordinary business payloads.

## 5. Freshness

Freshness MUST be evaluated centrally.

Illustrative policy categories:
- A0: normal session validity
- A1: recent authentication
- A2: recent step-up authentication
- A3: very recent phishing-resistant step-up plus transaction binding

Exact durations are a policy decision and must not be embedded independently in business services.

## 6. Evidence

The assurance service may consume validated IAM evidence such as:
- issuer
- subject
- authentication time
- authentication methods
- authentication context
- user verification
- phishing-resistance indication
- session state
- step-up event evidence

The Identity Adapter owns protocol-specific validation and mapping.

## 7. Failure Semantics

Insufficient assurance MUST produce a deterministic denial such as:

INSUFFICIENT_AUTHENTICATION_ASSURANCE

The caller must not receive secrets or implementation details.

The system should be able to distinguish:
- unauthenticated
- authenticated but insufficient assurance
- authorization denied
- transaction authorization required
- transaction authorization invalid/expired/replayed

## 8. Downgrade Protection

A request requiring A2 or A3 MUST NOT proceed because a lower assurance context exists.

An attacker must not be able to:
- edit assurance level
- replace stronger evidence with weaker evidence
- replay old step-up evidence
- substitute another principal
- reuse transaction approval

## 9. Ownership

ZITADEL/Keycloak:
- identity
- authentication
- MFA/passkeys
- protocol-level authentication evidence

EasyChatBot:
- identity adaptation
- assurance policy
- application authorization
- transaction authorization
- risk context
- audit/evidence correlation

## 10. Out of Scope for W15.6

- production ZITADEL deployment
- Keycloak deployment
- WebAuthn implementation
- transaction authorization implementation
- business-service gates
- replacing the existing password/session system

Those belong to later W15 stages.
