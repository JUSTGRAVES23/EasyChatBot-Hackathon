# WS-21.15 — Security Verification

## Data boundary

The browser receives sanitized operational data only.

## Explicit prohibitions

The E2E verification must prove that the dashboard cannot expose:

- Telegram bot token
- database URL
- database password
- LLM API key
- provider credentials
- learner messages
- prompts
- model responses
- authorization headers

## Identity

A Telegram user may be identified only through the controlled operational user reference supplied by the authorized backend contract.

Raw identity must not be inferred from arbitrary event payloads.

## Failure handling

Dependency exceptions must be transformed into safe operational states.

The browser must never receive:

- stack traces
- raw exception messages containing credentials
- connection strings
- internal filesystem paths
- provider authentication details

## Logging

Operational logs may contain technical diagnostic information subject to the platform logging/security policy, but such information must not be copied into the learner-facing dashboard response.

## Read-only guarantee

E2E verification must confirm the dashboard does not:

- send classroom messages
- publish announcements
- modify provider routing
- modify PostgreSQL
- execute remediation
- change Runtime policies
