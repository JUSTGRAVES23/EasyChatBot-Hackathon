# WS-22.3.2 — Durable Execution & Idempotency

## Scope

This slice hardens the WS-22.3.1 execution contract with durable execution
state and persistent idempotency.

### Included

- durable execution record contract
- execution attempt/status
- idempotency key
- correlation ID
- provider message ID
- success/failure persistence
- restart-safe duplicate detection
- audit integration
- retry-safe application orchestration
- regression tests

### Explicitly excluded

- Telegram-specific logic
- frontend changes
- publication UI
- direct provider integration

## Existing persistence architecture

The SQLAlchemy adapter accepts an injected `async_sessionmaker`. It therefore
does not create a new database connection manager or application-wide session
architecture.

Before production integration, register `PublicationExecutionRecordModel`
with the repository's existing declarative Base and migration system. Do not
create a second metadata/database stack.

The unique primary key on `idempotency_key` is the durable duplicate-execution
guard.

## Retry semantics

- `SUCCEEDED`: never execute the same idempotency key again.
- `FAILED`: may be retried using a new execution attempt/key according to the
  application retry policy.
- `STARTED`: represents an interrupted/in-flight attempt and must be reconciled
  by the execution policy before another external send is allowed.

For real multi-worker execution, the create-started operation must be
transactionally protected by the database unique constraint.

## Security

Only stable error codes are persisted. Raw provider exception text,
credentials, prompts, learner content, and sensitive metadata are not stored
by this slice.
