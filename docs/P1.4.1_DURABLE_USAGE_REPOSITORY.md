# P1.4.1 — Durable Provider Usage Repository

## Objective

Establish the PostgreSQL infrastructure adapter for the existing
`ProviderUsageRepository` contract.

## Architecture

ProviderUsageEvent
    -> ProviderUsageService
    -> ProviderUsageRepository
    -> PostgreSQLProviderUsageRepository
    -> ProviderUsageRecord

The application contract remains independent of SQLAlchemy.

## Design decisions

- Reuse the canonical SQLAlchemy `Base`.
- Reuse the existing synchronous session factory because the existing
  ProviderUsageRepository contract is synchronous.
- Keep the model in infrastructure.
- Preserve Decimal cost and UTC timestamp values.
- Preserve the existing in-memory repository for unit tests.
- Do not change provider adapters.
- Do not change Operations Center.
- Do not modify Telegram.
- Do not create or execute an Alembic migration in P1.4.1.

## Migration boundary

The database table is intentionally a P1.4.2 concern. The integration
test skips when the table does not exist, allowing the repository contract
and persistence adapter to be validated without altering the shared
database migration state.

## Known limitation

`ProviderUsageEvent` currently does not contain `provider_request_id`.
P1.4.1 therefore persists the existing event contract only. Adding request
identity should be handled as an explicit contract change rather than
silently dropping it or placing it in an unrelated column.
