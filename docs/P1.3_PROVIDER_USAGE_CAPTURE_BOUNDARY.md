# P1.3 Provider Usage Capture Boundary

## Objective

Connect the canonical live `ProviderResult` to the existing provider usage
intelligence contract without moving accounting responsibilities into the
provider adapters or Operations Center.

## Flow

Provider adapter -> ProviderResult -> ProviderUsageCapture ->
ProviderUsageEvent -> ProviderUsageService -> ProviderUsageRepository

## Responsibilities

`ProviderUsageCapture` owns application attribution:

- capability
- functionality
- agent
- optional quality score
- estimated cost supplied by the application/pricing boundary

Provider adapters own provider-neutral execution metadata:

- provider
- model
- request ID
- token usage when exposed
- latency
- success/error

## Compatibility

The capture boundary does not change `ConversationRuntime.respond()`, whose
public return value remains `str`. It can therefore be introduced and tested
without changing Telegram transport or Telegram conversation contracts.

## Current limitation

The existing `ProviderUsageEvent` requires concrete token counts and latency.
When the canonical provider result has unavailable counters, this boundary
uses zero only to satisfy the legacy usage intelligence contract. The
canonical `ProviderResult` remains the source of truth for whether provider
native metrics were actually available.

Estimated cost is never calculated here. It is supplied explicitly by the
application/pricing boundary and defaults to zero for the current capture
contract.

## Non-goals

- database persistence
- provider API calls
- dashboard changes
- billing API integration
- Operations Center changes
- changes to Telegram service contracts
