# WS-22.3.2.x.1 Scope

## Objective

Verify the existing WS-22.3.2 durable execution implementation against real
PostgreSQL after a simulated application restart.

## In scope

- PostgreSQL connectivity through the existing DATABASE_URL.
- Existing SQLAlchemy execution repository.
- Existing durable execution service.
- Durable success persistence.
- Durable failure persistence.
- Correlation ID persistence.
- Provider message ID persistence.
- Idempotent replay after a new service/repository instance.
- Retry after a persisted FAILED state.
- Cleanup of test rows.

## Explicitly out of scope

- New application services.
- New domain models.
- New repositories.
- Telegram.
- Frontend.
- Changes to WS-21.
- Changes to the publication/template model.
- Changes to Alembic migrations.

## Acceptance criteria

1. Successful execution persists in PostgreSQL.
2. New repository/service instances can recover it.
3. Same successful idempotency key returns IDEMPOTENT_REPLAY.
4. Publisher is not called during successful replay.
5. Provider message ID persists.
6. Correlation ID persists.
7. FAILED state persists after restart.
8. Failure can be retried using the existing service semantics.
9. Retry updates the same durable execution record rather than creating a
   duplicate idempotency record.
10. No production code abstraction is introduced.
